Design only; nothing here is implemented. Base: `main` `be2089f` (v2.9.5). Authority: owner decision D12 (week plan
`.compass/results/2026-09-25_week-plan-paired-session.md`, 2026-10-03 15:30: "v2.10.0 = paired-session default with the
real lifecycle at legacy parity, after the stable real runs") and D-1..D-8 (same file, 2026-10-03 18:02; D-4: lifecycle
on only from CLI or operator profile, the v2.10.0 skill turns it on). Lifecycle implementation is lane A option W

[1d-entry-mapping.md](1d-entry-mapping.md) (v2.9.0 opt-in), [`docs/paired-session-migration.md`](../../docs/paired-session-migration.md),
`DECISIONS.md` ADR-6. Line numbers are against `be2089f`. Owner decisions E-1..E-12 are in section 8,
named E-* so they do not collide with D-1..D-8; the owner decided all twelve as recommended (2026-10-04, week plan
entry 2026-10-04 02:30), so each "recommended" option below is now the decided one. "Proposed" text is a draft for review, not
a decided string.

## 0. Summary
- **Default entry** means: a fresh `/review-loop <work item>` (Claude) or a fresh review-loop request (Codex) whose
  `.review-loop/config.md` has **no `entry` key** hands off to the paired-session skill, which runs the coordinator with
  `--lifecycle-mode on` (PLAN, EXEC, gate, FINISH, POLISH-Q, DOCS, SECURITY, DONE, operator accept). Everything else keeps
  its v2.9.5 route: plan-exists, code-exists and existing-session states, `/review-loop:plan`, `execute`, `review-pr`,
  `/review-loop:legacy` and `entry: legacy` stay legacy.
- **Opt-out** needs no reinstall: `entry: legacy` (a valid value since v2.9.0, so it can be set before upgrading),
  `/review-loop:legacy`, or the Codex phrase "use the legacy review-loop workflow".
- **Failure rule (proposed, E-3):** one boundary, the first command that runs `bin/paired-session`. A precondition that
  fails before it (stage A) falls back to legacy with a printed notice only under the implicit default; with an explicit
  `entry: paired-session` or `/review-loop:paired-session` it refuses. From that command on (stage B), every refusal or
  failure is reported as REFUSED/HOLD and never falls back (the v2.9.5 rule, `skills/review-loop/references/entry.md:73-74`).
  No path switches silently.
- **Earliest flip:** the release that contains lane A W3b and lane B's FIELD-1, FIELD-10 and FIELD-11 fixes, meets the
  stable-run gate (E-1), and has the owner's answer on the earlier routing gates (1C closure and M6; M4's fake E2E shipped in v2.9.3; E-12). Three
  preparatory units (U0, U1, U2) can land before that without changing behavior.

## 2. Opting out, and what happens when a precondition fails

### 2.1 Opt-out paths (none needs a reinstall)
1. `entry: legacy` in `.review-loop/config.md` (`skills/review-loop/references/entry.md:12`). Workspace-committed, so it
   applies to every clone; valid on v2.9.0+ and therefore safe to set before upgrading.
2. `/review-loop:legacy <work item>` (Claude, `skills/legacy/SKILL.md:25-28`).
3. Codex: "use the legacy review-loop workflow" (`.agents/skills/review-loop/references/entry.md:17-19`).
4. `/review-loop:plan`, `execute`, `review-pr` are unaffected by `entry` (E-8).
5. If the switch itself is wrong: the maintainer's fix-forward release (section 7.3).

## 3. lifecycle_mode=on through the skill (D-4) and the dispatch preconditions

### 3.1 How the flag is set
- One rule. A **new run** gets `--lifecycle-mode on` on `permission-probe` and `run`, identically (today's rule: one-run
  overrides go to both calls, `skills/paired-session/SKILL.md:86-87`; `.agents/skills/paired-session/SKILL.md:60-64`).
  Every **later command on an existing run** (`resume`, `permission-probe --retry-uncertain`, `abort`, `reject`, `accept`,
  `note`, `attach-verification`) passes the saved `state.json` `config.lifecycle_mode`, never the current default
  (details in the last bullet). Plain `status` prints `state.json` without building a coordinator
  (`coordinator.py:6567-6568`) and needs no flag. Whether
  lifecycle mode enters the probe binding is W1a's choice; passing the same value to probe and run keeps the skill
  independent of that answer.
- Under E-7 (a), the recommendation: CLI beats profile (`coordinator.py:6503-6512`), so an operator profile with
  `"lifecycle_mode": "off"` (the shipped example, `paired-session-config.example.json:14`) does not turn the default entry
  into a DONE-only run. Under E-7 (b) the skill omits the flag when the profile sets the key.
- Never via the workspace profile and never by changing the parser default (`coordinator.py:6337` stays `off`; D-4, parity
  map D-4 note: flipping the parser default touches every real-EXEC test).
- Why the saved value: every action except `accept`/`reject`/`note`/`attach-verification` (and `status`) validates the
  arguments key by key against the saved configuration, `lifecycle_mode` included (`_validate_resume_args`,
  `coordinator.py:1289-1290`, `:1951`, `:1986-2003`; `lifecycle_mode` is a config key, `:1468`; "effective settings must still
  match the saved run configuration", `paired_session/README.md:97-98`), so `abort` without the saved value is refused,
  while for `accept`/`reject`/`note`/`attach-verification` the restore loop already copies every saved config key,
  `lifecycle_mode` included, over the arguments (`coordinator.py:1276-1284`), but only after the `__init__` lifecycle check
  (`:1214-1218`), which sees the pre-restore argument. Passing the saved value is correct in both cases. A v2.9.x run (`off`) continued
  under v2.10.0 stays `off` and ends at DONE.

## 7. Rollout and rollback

### 7.1 Upgrade notes (draft for CHANGELOG, Chinese in the release)
- Fresh `/review-loop` without an `entry` key now runs paired-session with the full lifecycle; it prints the
  default-entry notice. To keep legacy, set `entry: legacy` before or after upgrading.
- Needs macOS, the CLIs for the configured roles (default: Codex author and gate, Claude reviewer), a dedicated worktree
  and a test command. Missing prerequisites fall back to legacy with a notice (implicit default only, E-3).
- The probe PASS is bound to the plugin version; existing probe reports and caches are void after the upgrade (as in
  every v2.9.x note, `CHANGELOG.md:7`). Do not change versions in the middle of a run.
- Runs started on v2.9.x keep `lifecycle_mode=off` on resume and end at DONE.
- Legacy plans and sessions are never imported; non-fresh work stays legacy.

### 7.2 Pinned-copy practice
- CLI-driven paired runs keep using a pinned copy, `~/paired-runs/review-loop-v<version>` (`CHANGELOG.md:7`); v2.10.0
  adds `~/paired-runs/review-loop-v2.10.0`. A run is resumed only with the copy that started it.
- Skill-driven runs use `${CLAUDE_PLUGIN_ROOT}` (Claude) or the cache path resolved from `codex plugin list`
  (`.agents/skills/paired-session/SKILL.md:38-40`); the version that started a run must finish it. The skill records the
  plugin version in its report.
- This repository: owner rule 2026-10-03 15:15 (pinned copy, external `--config`, separate clone, never
  `entry: paired-session`). U0 makes that hold under the new default.

### 7.3 Rollback
- User level, no reinstall: section 2.1. A routed run already in progress is stopped by letting its current command
  finish (or stopping it and waiting for the child to exit, S7), then `paired-session abort` with the run's saved
  workspace, work item, run directory, profile and options, including the saved `--lifecycle-mode` (section 3.1;
  `abort` is validated against the whole saved configuration, `coordinator.py:1952-1953`, `:1986-2003`); the run directory
  stays as evidence. With `auto_commit` false nothing was committed; with `auto_commit` true a local commit
  exists only after `accept`, and the user reverts it with `git revert`.
- Plugin level is fix-forward, as recorded for v2.9.0 (`v2.9.0-release-checklist.md:35`: "bump to 2.9.1 … Users pin the
  previous version by `plugin update` after 2.9.1"): the maintainer releases v2.10.1 that reverts U3-U5 (the entry text)
  and keeps the lifecycle; users get it with `plugin update` and a new session (CLAUDE.md "Plugin cache & version bump").
  A revert needs its own bump and tags are never moved. No downgrade mechanism is assumed.
